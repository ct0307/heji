# M4 004 备份与恢复设计

日期：2026-11-19。设计、v2代码及离线验证已完成；后续三项独立许可下bench 004、新备份和独立恢复均已执行，见[真实验收](m4-backup-restore-004-real-verification.md)。完整性通过，恢复41分20.52秒，30分钟目标未通过；以下设计阶段的“不执行”边界不作为当前待办或重复操作许可。

## 目标

在保留旧 M4 备份与恢复证据的前提下，为含 004 结算窗口表的 M4 隔离库增加可验证的备份与恢复路径。旧格式继续支持 001/002 与 003 后结构；新格式明确记录迁移清单和校验和，并且只能恢复到新的固定隔离库 `heji_m4_restore_004`。

本设计不迁移 `heji_m4_bench`，不触碰 `heji_dev`、`heji_m4_restore` 或 `heji_m4_restore_003`，不创建备份、不导入真实数据库、不清理数据，也不更改普通迁移入口、财务行为或 004 SQL。

## 方案与兼容性

- 001/002、003 后结构沿用现有 v1 格式与恢复目标；不改写旧备份、校验清单或验收证据。
- 含 004 的备份使用新的 v2 头部格式，记录格式版本、固定 fixture 版本、完整 schema 和按名称排序的迁移名称/校验和清单。压缩文件摘要和逐表摘要继续覆盖整个备份内容。
- v2 只接受完整且有序的 001、002、003、004 迁移清单；004 校验和必须与当前独立提案源文件一致。缺标记、多余迁移、混合结构、只有部分汇总表、缺少窗口表或表结构不一致时拒绝备份/恢复。
- 恢复根据备份头部识别 v1 或 v2，按对应版本创建空结构并核对迁移校验和。v1 的解释和目标保持原样；v2 只能使用新的固定目标 `heji_m4_restore_004`。任意自定义目标、已存在目标和不受支持的版本都拒绝。
- `settlement_windows` 中的已关闭记录属于账本审计上下文，保留在备份中；存在任何未关闭且未过期的活动窗口时拒绝创建备份，避免恢复后遗留一个仍有效的短时财务写入锁。已到期但未关闭的行按当前应用语义处理为非活动状态，并在恢复验收中确认没有活动窗口。

## 备份流程

1. 在 M4 隔离门禁、本机数据库及一致性只读快照内读取 `schema_migrations`、表架构与 fixture 元信息。
2. 当且仅当结构和迁移标记完整匹配 001–004 时选择 v2；否则沿用完整匹配的 v1 路径或在版本/结构不一致时停止。不得仅凭某张表存在来推断迁移完成。
3. 对 v2 检查 `settlement_windows` 不含活动窗口。窗口表中的历史行不删除、不重写。
4. 对所有表按稳定主键顺序导出，记录逐表行数和 SHA-256，并生成压缩文件 SHA-256 清单。文件只在 `.local/m4/` 下以独占创建方式保存；不得输出行内容、凭据或本地连接配置。
5. 任一检查或写入失败时保留已产生的残留文件用于诊断，不自动删除或覆盖；失败清理另行授权。

## 恢复流程

1. 在导入前验证本地系统生成文件名、普通文件（拒绝符号链接）、压缩长度、整体 SHA-256、头部版本、完整迁移清单、表序、每行字段类型、逐表摘要和总行数。
2. 仅接受备份对应的固定目标：旧版本仍由现有目标规则处理；v2 只能指定 `heji_m4_restore_004`。目标必须不存在，MySQL 连接必须是本机。
3. 为 v2 创建空 001–004 结构及精确迁移标记，再导入备份行；不执行备份中的 SQL。窗口表结构使用当前固定迁移源重建，并与备份头部逐列比较。
4. 导入后验证迁移名称/校验和、每张表的行数与 SHA-256、全部外键、历史/当前分摊守恒、账本余额守恒、003 派生余额和期间报表与原始事实一致，以及 `settlement_windows` 活动窗口数为 0。
5. 全部检查成功后提交并生成只含脱敏元信息的本机验收证据。中途失败时停止并保留新目标及残留，禁止 DROP、清库或自动重试。

## 离线测试

- 通过合成 schema/迁移清单验证 v1/v2 选择、完整迁移顺序、校验和匹配、汇总表全有或全无、窗口表缺失/多余及结构不匹配。
- 验证活动窗口拒绝、关闭窗口历史保留，以及到期窗口不被误判为活动窗口。
- 验证 v2 只接受 `heji_m4_restore_004`，v1 目标行为未变；任意目标、重复目标参数和已存在目标仍会拒绝。
- 验证文件头、清单、行数、逐表摘要或迁移清单任一被篡改时，在建库前拒绝；离线测试不连接 MySQL、不读取 `.env`、不启服务或写数据库。
- 完成后运行 `npm test`、`npm run typecheck` 和 `npm run build`。这些检查不能代替真实 004 备份恢复验收。

## 独立操作许可

代码和离线测试审阅通过后，真实验收仍分为三项独立操作，不由本设计或既有授权自动包含：

1. 将 004 迁移到 `heji_m4_bench`，明确确认目标、停写维护窗口和失败残留策略。
2. 从 `heji_m4_bench` 创建一次新 v2 备份，明确同意保留新文件和数据库新增数据。
3. 将该备份恢复到新目标 `heji_m4_restore_004`，明确同意创建该库及保留失败残留；不覆盖、不清理既有恢复库。

三项各自记录实际起止状态、迁移清单、逐表摘要与限制。没有真实备份和恢复证据前，不得称 004 兼容验收完成；公网/生产验收仍独立开放。

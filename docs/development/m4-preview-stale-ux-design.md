# 转账预览过期后的重新确认设计

状态：用户已审核通过；实现及HTTP浏览器回归已完成。

## 背景

M4正式基准显示，同账本并发确认0/3364成功，全部以`409/PREVIEW_STALE`拒绝；分散账本确认4259/4259成功。服务端拒绝旧财务版本是正确的安全行为，但当前客户端把所有409统一处理为关闭预览，要求用户回列表重新打开，热点账本下的核对体验较差。

目前实现位于`apps/web/src/components/SettlementPanel.vue`：`confirm()`捕获409后清空`preview`和`acknowledged`，随后刷新请求列表和父级财务快照。API客户端`ClientFault`同时提供HTTP状态和业务错误码。预览接口返回请求、预期请求修订号、预期财务版本和确认前后双方余额。

## 目标

- `PREVIEW_STALE`后自动读取同一笔待确认请求的最新预览并保留在确认面板中。
- 显示最新请求金额、请求内容及双方确认前后的余额。
- 清除此前的确认勾选；用户必须查看新预览、重新勾选并再次点击确认。
- 每次用户点击最多发送一次确认POST；收到冲突后只自动发送一次预览GET，不自动重试确认。
- 服务端版本校验、请求修订校验、幂等保护与账本授权保持不变。

## 交互流程

1. 用户勾选并点击确认，客户端发送一次确认POST，内容使用当前预览中的`expectedRequestRevision`和`expectedFinancialVersion`。
2. 若返回`409/PREVIEW_STALE`，客户端立即清空勾选状态，保持确认面板，显示“账本在核对期间已有变化；以下是最新预览，请重新核对后确认”。
3. 客户端对同一请求ID执行一次预览GET；成功后用最新DTO替换面板中的预览，显示最新请求金额、日期、说明及双方确认前后余额，并通知父级刷新余额/报表。
4. 确认按钮保持禁用，直到用户重新勾选。只有用户再次点击后才发送新的确认POST。新版本参数会改变请求体，现有意图存储据此生成新的幂等键。
5. 若用户再次确认时又发生版本变化，重复上述“单次刷新、清除勾选、用户重新确认”流程；不形成自动POST循环。

## 错误处理

- 只对`status===409 && code==='PREVIEW_STALE'`触发自动预览GET。其他409错误不冒充版本过期，沿用通用冲突处理。
- 预览GET失败时清除面板中的旧预览和勾选状态，保留明确错误；用户可从仍可用的待确认列表重新打开预览。不得在旧版本上启用确认按钮。
- 若请求已取消、拒绝或确认，按预览接口的权威响应处理，不显示旧预览，也不重试确认。
- 网络错误、401和授权错误沿用API客户端现有会话及错误处理，不绕过权限、不缓存或展示过期预览供提交。
- `busy`继续阻止并发重复点击；请求登记、拒绝、取消及冲正流程不改变。

## 范围

仅调整结算确认面板及所需的前端状态处理和回归测试；不改API、数据库、汇总表、基准口径、数据模型或财务规则。无需新增依赖。预览面板沿用现有布局，在窄屏下继续单列显示双方余额；变化提示使用可访问的状态/错误语义。

## 验收

- 冲突返回后，确认面板保留且显示最新预览；旧确认勾选被清除。
- 过期后网络记录为一次确认POST和一次预览GET；没有自动第二次确认POST。
- 用户重新勾选并确认时使用最新请求修订号、财务版本和新的幂等键。
- 连续两次版本冲突每次都需要用户重新查看、勾选和点击。
- 预览GET失败时旧预览不可确认；非`PREVIEW_STALE`的409不触发该刷新路径。
- 财务服务端过期版本回归继续拒绝确认；只有真实成功确认才影响余额。
- 通过现有普通测试、类型检查和构建；条件允许时验证桌面与手机面板。浏览器自签证书信任问题须先按授权范围解决，不得绕过证书警告。

## 尚不包含

不自动接受新余额、不代替用户再次确认、不降低`PREVIEW_STALE`保护、不把确认当成实际支付，也不修改M4性能统计中的冲突计数。该改动是交互恢复，不承诺在持续并发下提高确认成功率。

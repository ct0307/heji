# 短时结算窗口设计

日期：2026-11-19。状态：用户已审核批准，代码、heji_dev的004迁移及真实多连接5/5（含父测试）完成；本轮独立3账号/3账本浏览器8组最终检查通过，限制见[UI记录](m4-settlement-window-ui-plan.md)。bench未迁移004，新负载及004恢复尚未验收，热点P1保持开放。实际范围与后续门禁见 [实现与验收记录](m4-settlement-window-verification.md)。

## 问题与目标

正式热点确认0/3364，预览到确认取得账本锁期间财务版本通常前进约17次。用户决定继续保留全账本financialVersion门禁，并选择设计一个超时自动解除的结算窗口。

窗口通过短暂暂停同账本其他财务写入，给指定确认者一次人工核对机会。确认仍比较financialVersion和请求revision；窗口不是付款确认，不自动续期，不自动重试确认，不保证所有负载下均可申请或确认成功。原正式和参与范围证据不修改。

## 方案比较与选择

| 方案 | 成本与行为 | 决策 |
|---|---|---|
| 人工协调停止录入 | 无新表，不阻止其他用户继续写入；不能保证核对期间版本稳定 | 仅保留为当前演示操作建议，不作为P1修复 |
| 数据库短时结算窗口 | 暂停同账本其他财务写入；需要新表、后端入口、UI、并发及真实运行验证 | 用户选择的方向，本稿细化此方案 |
| 仅在单个Node进程内暂停 | 重启丢失、多实例和M1入口可能绕过，难以统一保护 | 不采用 |

## 默认参数与权限

- 每账本最多一个窗口，绑定一笔PENDING普通转账或冲正请求、该请求的counterpartyMemberId及当前确认者userId。
- 当前有效成员且为请求指定确认者才可申请；账本归档、请求终态或未经授权均拒绝。任何UUID都只作标识，不代替当前会话、成员和对象授权。
- 固定30秒，使用数据库UTC时间。无续租、后台续期或失败后自动重新申请。浏览器倒计时仅提示，数据库时间是最终判断依据。
- 窗口结束后同账本冷却30秒，确认成功、取消、主动关闭与自然到期都适用。冷却期间普通写入完全开放，但新窗口申请返回明确剩余时间。不能用新幂等键绕过冷却。
- 以上时长已获用户审核；若30秒不足，先记录实际核对时长再改设计，不默默增加锁定时间。

## 写入边界

| 操作 | 活跃窗口内处理 |
|---|---|
| 余额/报表/明细/成员等读取、登录注销 | 正常；已有授权继续生效 |
| 支出新增、全部PATCH（含备注）、作废 | 返回409 SETTLEMENT_WINDOW_ACTIVE及可读提示，草稿保留，不自动重发 |
| 其他转账登记/确认/冲正申请、成员退出/移除、归档/恢复 | 暂停新写入，返回同类冲突；不跳过原有对象授权 |
| 接受邀请或重新加入 | 必须在M1事务的账本锁内检查窗口并暂停；该入口会推进财务版本 |
| 账本重命名、邀请创建/撤销 | 仍可按原授权执行；不改变余额或成员，不能隐式续期或释放窗口 |
| 窗口绑定请求的确认 | 只有绑定确认者、有效窗口ID、最新财务版本和请求revision全部匹配才执行；成功入账并同事务关闭窗口 |
| 绑定请求的取消/拒绝 | 原发起者仍可取消、指定对方仍可拒绝；改变请求终态并同事务关闭窗口 |
| 关闭窗口 | 持有人或账本创建者可主动关闭；创建者不能借此代替另一方确认。窗口ID必须匹配，旧关闭请求不能关闭新窗口 |
| 已成功幂等操作的重放 | 重新鉴权及对象授权后可返回原结果，不产生新事实；不能被新窗口误当新写入。被窗口拒绝的意图不记录为已成功 |

普通确认接口保留兼容路径：无活跃窗口时仍按原版本门禁确认。活跃窗口时即使版本相同，非绑定请求/确认者也不能写入。只检查“是否推进financialVersion”不够，窗口还保护绑定请求状态和完整核对上下文。

## 数据模型与事务

新增独立迁移004（文件名在实施计划确定），不修改001/002/003。一张`settlement_windows`表以bookId为主键，保存windowId、requestId、holderUserId、holderMemberId、createdAt、expiresAt、closedAt、cooldownUntil；历史业务不删除，表内仅保存当前/最近窗口，生命周期审计另存事件。UUID列类型与既有表一致，bookId/requestId/memberId使用与既有模式一致的复合外键，避免跨账本引用。

所有申请、关闭及业务写入统一锁顺序：books行→当前成员授权→窗口行→业务对象/幂等记录。窗口检查使用当前读及锁内数据库时间，不能受REPEATABLE READ旧快照影响；M1接受邀请也采用相同顺序。不存在窗口行时依靠已有books锁串行首次INSERT，不采用跨请求长事务。

申请窗口是显式POST，在短事务内完成：鉴权→锁账本→对象权限/请求终态→幂等核验→活跃/冷却检查→写入窗口→读取同一事务内最新预览→再次检查未到期→提交。预览版本与窗口必须来自同一受保护状态。窗口申请、结束和冷却均不增加financialVersion或请求revision，不产生转账事实。

确认在短事务内核验原有请求版本、财务版本及窗口所有权/标识/期限，在财务变更前重读数据库时间。到期则拒绝窗口确认，不回退为普通确认。已通过检查的短事务持有账本锁完成原子提交；期限不是中断SQL事务的计时器。后续写入仍等待正常提交/回滚，不存在跨人工等待持有连接或锁。

自然到期不依赖定时任务：每次入口都把`expiresAt <= 数据库当前时间`视为失效，普通写入立即恢复，不等待清理；自然到期的冷却终点为expiresAt+30秒。显式结束时cooldownUntil=结束时刻+30秒。页面关闭、断网或进程重启不会留下永久阻塞；即便主动释放失败，最大逻辑窗口仍为30秒，另加正常事务完成时间。

数据库故障时返回503，不把窗口表查询错误当作“没有窗口”。004激活标记缺失时窗口入口明确返回不可用，原财务功能兼容旧结构；标记存在而表损坏时财务写入失败关闭。上线前必须升级全部M1/财务写进程，不能混跑绕过新检查的旧版本。

## HTTP与UI草案

| 接口 | 用途与响应 |
|---|---|
| `GET /books/{bookId}/settlement-window` | 当前成员读取是否活跃、到期时间/冷却时间、是否自己持有；他人不返回请求内容或私密数据 |
| `POST /books/{bookId}/transfer-requests/{id}/settlement-window` | 明确申请窗口，带CSRF和Idempotency-Key；返回windowId、服务器时间、到期时间及最新确认预览 |
| `POST /books/{bookId}/settlement-windows/{id}/close` | 持有人/创建者明确关闭；幂等、重新授权，旧ID不得影响后续窗口 |
| 既有确认接口扩展可选`expectedWindowId` | 窗口确认必须提交；原两种expected版本仍必需。成功重放仍返回原事实；过期返回409 SETTLEMENT_WINDOW_EXPIRED |

申请幂等响应不续期：原键重放只能得到原窗口ID/期限，已经过期或结束时标明状态，不能伪装为新活跃窗口。申请响应丢失时沿用原键核对结果；若窗口正在处理中，不并发创建第二个。明确新申请才生成新意图，仍受冷却限制。

UI在普通预览旁提供“短时结算窗口”主动按钮，说明会暂停该账本其他财务写入30秒；普通GET预览不自动申请。申请成功替换成窗口返回的新预览，清除旧勾选，显示倒计时及“关闭窗口”。只有用户重新核对、勾选、点击才确认。

到期或窗口失效后禁用窗口确认并清除勾选；重新查看普通预览，不自动申请、不自动确认。服务端仍会阻止修改后的windowId或过期版本。其他成员写入受阻时显示“有人正在核对结算，请稍后重试”，保留输入及原幂等意图，无自动POST循环。

窗口状态通过读接口补查；持有面板在重新可见时立即补查，倒计时到零本地禁用。首版不新增WS消息类型，不依赖通知保证正确性；其他成员提交时由HTTP权威响应解释冲突。关闭面板时可以尽力请求关闭，卸载失败不影响数据库到期恢复。新增请求的日志和截图沿用原敏感字段保护。

## 实施与验收顺序

1. 审核本稿参数、受阻范围与接口；再编写实施计划。先做纯规则/HTTP失败回归，不先改生产财务代码。
2. 实现共享窗口检查、M1/财务全部写入口、幂等重放、004迁移计划与UI；不新增依赖。普通迁移入口不自动执行004。
3. 离线测试与类型/构建：30秒边界、冷却、成员/请求授权、同/异账本、过期、旧ID关闭、重放、网络失败及回滚均覆盖。
4. 取得单独明确迁移许可后才对选定数据库执行004；已迁移库不得重跑001/002/003。新表不需要修改旧财务事实或重跑003汇总。
5. 取得本轮真实开发库写入许可后验证多连接竞争：两申请只得一个窗口；窗口内支出/邀请加入均被阻止；绑定确认只入账一次；到期普通写恢复；取消/拒绝释放；故障回滚无幽灵窗口。使用真实MySQL验证，不以模拟代替。
6. 浏览器检查正常申请/确认、空请求、其他人占用、到期、断网、刷新、跨标签、重复点击及360/390/768/1440布局；未迁移前不伪造UI通过。
7. 另获新负载许可后执行独立run，原12组和9轮研究不重跑、不覆盖。建议新增5秒/15秒人工核对等待场景；目标为有效窗口内、未主动取消且在到期前发起的确认成功率≥99%，确认HTTP P95≤800ms，系统故障率<1%。所有申请、过期/取消和未取得窗口的确认也单独公布总数及整体成功率，不用筛选后的99%冒充整体成功率。普通写入的成功/被暂停/延迟、窗口占用和冷却占比全部公开；若写入吞吐代价不可接受，即使确认达标也不关闭P1。具体流量轮数、写入成功率目标及运行时间须在实施后的负载方案中明确并另行审阅，不把原60/30/10连续写基准当作人工核对场景。

## 风险及完成条件

窗口把原来的确认饥饿转换为短暂的写入暂停，可能降低支出吞吐；冷却只能限制单账本窗口占用比例，不承诺申请公平或无饥饿。阻塞备注PATCH是首版保守边界。用户确认所需时间可能超过30秒，需要真实体验验证。全账本版本门禁的正确性测试始终保留。

本稿不能关闭热点P1。只有规格批准、实现、明确许可后的迁移、多连接/浏览器及独立新负载验收通过，且写入可用性代价被接受后，才可更新验收结论。公网/生产部署不包含在本设计许可内。
